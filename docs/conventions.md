## 1. Скелет кейса

Каждый кейс отвечает на пять вопросов в этом порядке. Порядок не переставляем —
он повторяет ход реальной работы и читается сверху вниз без прыжков.

| Блок | Что в нём | Объём |
|---|---|---|
| **Задача** | Вопрос бизнеса + решение, которое от ответа зависит | 2–3 предложения |
| **Данные** | Источник, период, объём, ключевые поля, лицензия | абзац + таблица |
| **Метод** | Что применил и почему именно это; бейзлайн для сравнения | 1–2 экрана |
| **Что не сработало** | Отвергнутая модель / не подтвердившаяся гипотеза / нехватка данных | 3–6 строк |
| **Решение** | Что делать бизнесу, с цифрой и условием применимости | 3–5 строк |

Блок «Что не сработало» обязателен. Это то, что отличает кейс от туториала:
показывает, что выбор метода был выбором, а не единственным известным вариантом.

## 2. README кейса — точный порядок секций

```markdown
# <Название кейса>

**TL;DR.** Одно предложение с главной цифрой и решением.

## Вопрос
## Данные
## Определение метрики
## Метод
## Результаты
## Что не сработало
## Рекомендация
## Ограничения
## Воспроизведение
```

Правила:

- **TL;DR** — первое, что видит читатель. Должен быть понятен без остального текста.
  Содержит число. Плохо: «проанализировал LTV пользователей».
  Хорошо: «Топ-20% по прогнозному LTV дают 61% выручки; BG/NBD обгоняет
  наивный бейзлайн на 23% по MAE на holdout».
- **Определение метрики** — что именно считаем, до всякого моделирования. Для LTV:
  горизонт прогноза, единица (валюта, gross или net), что вычитается (возвраты,
  скидки, налоги), дисконтирование да/нет с обоснованием, момент t₀ отсчёта.
  Для A/B — primary-метрика и её знаменатель. Для дашборда — определение
  North Star. Формулировка даётся как согласование с тем, кто считает деньги,
  а не как методическое предпочтение: «net revenue после возвратов внутри
  горизонта, потому что так считает финансовая отчётность».
  Абзац плюс формула. Без этого блока «Метод» не читается: непонятно, что
  предсказывается.
- **Результаты** — графики с подписанными осями, единицами и подписью под картинкой,
  объясняющей, что на ней видно. Картинка без подписи не считается результатом.
- **Ограничения** — 3–5 строк, не абзацы. Где модель врёт и при каких условиях.
- **Воспроизведение** — команды, которые работают с чистого клона.

## 2а. Корневой README — витрина

Витрина рассчитана на три разные глубины чтения, и все три должны работать
без перехода по ссылкам:

1. **Одна строка на кейс** — исход с цифрой. То, что прочитает рекрутер.
2. **2–3 буллета на кейс** — что сделано, каждый с числом и единицей. То, на чём
   остановится нанимающий менеджер.
3. **Ссылка на README кейса** — полный текст. Для того, кто будет проверять код.

```markdown
### LTV: прогноз и сегментация клиентской базы
Топ-20% по прогнозному LTV дают 61% выручки holdout против 44% у наивного бейзлайна.

- BG/NBD + Gamma-Gamma на <N> клиентах, calibration/holdout split по времени
- MAE на уровне пользователя ниже исторической суммы на 23%, Gini 0.51 → 0.64
- Сегментация по прогнозу: правило отсечки для VIP-программы, <цифра> бюджета

[Разбор кейса →](case_ltv/README.md)
```

Буллет без числа в витрину не идёт. «Построил когортный анализ» — это не
достижение, это название шага; шаги живут в README кейса.

## 3. Правила именования

**Папки кейсов:** `case_ltv/`, `case_ab/`, `case_dashboard/`
Без числовых префиксов. Порядок чтения задаёт корневой `README.md` — он же витрина.

**Ноутбуки:** `NN-глагол-существительное.ipynb`, snake_case, латиница.
```
01-load-and-profile.ipynb
02-cohorts-retention.ipynb
03-bgnbd-fit.ipynb
04-holdout-validation.ipynb
05-segments-and-decision.ipynb
```
Один ноутбук — один логический шаг. Ноутбук, который делает всё, не читают.

**Модули:** `src/` — snake_case, чистые функции, без print'ов в логике.
`src/features.py`, `src/models.py`, `src/plots.py`, `src/metrics.py`

**Графики:** `reports/figures/NN-описание.png`, dpi ≥ 150.

**Данные:** лежат **вне репозитория**, на уровне контейнера:
`Product_Analytics_Portfolio/data/{raw,interim,processed}/`.
`raw/` — как скачал, не трогаем. В репозиторий едет только скрипт загрузки.
Доступ к путям — через `paths.py` в корне репо, литеральных `../../data` в коде нет.

**Ветки:** `case/ltv`, `case/ab`, `case/dashboard`. Мерж в `main` по готовности кейса.

## 4. Формат выхода

**Что публикуется на GitHub:**
- README верхнего уровня (витрина: три кейса, три TL;DR, три ссылки)
- README каждого кейса
- Ноутбуки с выполненным выводом (чтобы читались прямо на GitHub)
- `src/`, `requirements.txt`, скрипт загрузки данных
- Картинки в `reports/figures/`

**Что не публикуется** (и физически лежит вне репозитория):
- `data/` — сырые и обработанные данные
- `ltv-clv-library/` — статьи, конспекты, черновики
- Рабочие журналы `case_*.md`
- `cv_claims_map.md`

Контейнер `Product_Analytics_Portfolio/` сам по себе не репозиторий. Всё,
что не должно уехать на GitHub, лежит соседней папкой с репо, а не внутри него
под `.gitignore`. Так случайный `git add -A` физически не может их захватить.

## 5. Технические правила

- `RANDOM_SEED = 42` в одном месте, и из него — **один именованный
  `numpy.random.Generator` на прогон**, который передаётся явно везде, где есть
  случайность: инициализация, сплиты, бутстрап, сэмплеры. Глобальное состояние
  numpy (`np.random.seed`, `np.random.rand`) не используется — оно не влияет на
  `default_rng` и создаёт видимость воспроизводимости.
- `requirements.txt` с прибитыми версиями (`pandas==2.2.3`, не `pandas`).
- Ноутбук перед коммитом прогоняется целиком с нуля: `Restart & Run All`.
  Ноутбук с разорванной нумерацией ячеек в репозиторий не едет.
- Пути только через `paths.py`: `from paths import RAW, PROCESSED, LIBRARY`.
  Никаких `pd.read_csv("../../data/raw/...")` в ноутбуках — ломается при переносе.
- Любая цифра в README воспроизводится ячейкой ноутбука. Цифр «из головы» нет.

## 5а. Проверки перед публикацией числа

Правила сняты с разобранных источников в `ltv-clv-library/notes/`: каждое
соответствует ошибке, которую автор не заметил и которая прошла в публикацию.
Все шесть ловятся ассертом в две-три строки. Ассерт стоит в коде, а не в голове:
дефект этого класса не выдаёт себя ни исключением, ни подозрительной метрикой.

**1. Параметрическое среднее сверяется с эмпирическим до любой интерпретации.**
У Gamma два соглашения (rate и scale) с одинаковыми буквами, и перепутанные
параметры дают правдоподобный на вид график. Для BG/NBD: `r/alpha` против
`(frequency / T).mean()` — совпадать они не обязаны (первое условно на «жив»),
одного порядка обязаны.
```python
assert abs(np.log10(r/alpha) - np.log10((f/T).mean())) < 1, "rate vs scale?"
```
*Источник: `notes/2026_Antonio_TDS-bg-nbd-series.md`, Part 2 ош. 2 и Part 3 ош. 1–2
(расхождение в 48 раз, прошло через три статьи).*

**2. Величина, названная «фактом», собирается из сырых данных.**
Не выводится арифметикой из производной колонки библиотеки. Если понадобилась
поправка на константу — значит непонятно, что в колонке лежит, и надо пересчитать
из источника. `frequency` в калибровке и в holdout означают разное.
```python
real = (tx.query("@cal_end < date <= @obs_end").groupby("customer_id").size()
          .reindex(rfm.index, fill_value=0))
assert (real == rfm["frequency_holdout"]).all()
```
*Источник: там же, Part 2 ош. 1 (единственная метрика статьи посчитана против
факта, завышенного на единицу у всех клиентов).*

**3. Ноль отличается от «нет данных».**
Колонка, не определённая для части клиентов (`monetary_value` у тех, у кого нет
повторных покупок), не идёт множителем. Доля нулей на выходе сверяется с долей
клиентов, у кого величина не определена; совпадение — артефакт, а не результат.
```python
assert not np.isclose((value == 0).mean(), (rfm.frequency == 0).mean(), atol=0.02)
```
*Источник: там же, Part 2 ош. 5 (56% базы получили LTV ровно 0 по построению);
`notes/2026_Kaggle-anon_online-retail-ii-rfm-kmeans-clv.md` — тот же класс через
`fillna` после `merge`.*

**4. Сомножители в формуле ценности не делят условие.**
`predict` у BG/NBD уже проинтегрирован по «жив/мёртв»; умножение на `p(alive)`
применяет скидку второй раз и искажает не уровень, а ранжирование — сильнее
всего в сегменте «покупали, но давно». Каждый множитель сопровождается строкой
«что это за ожидание и по чему проинтегрировано».
*Источник: `notes/2026_Antonio_TDS-bg-nbd-series.md`, Part 2 ош. 4.*

**5. Параметры постериора извлекаются одним общим индексом draw.**
Независимая пересэмплировка разрушает совместное распределение: на выходе
произведение маргиналов, а не постериор, и интервалы на любой нелинейной функции
параметров неверны.
```python
post = trace.posterior.stack(sample=("chain", "draw"))
idx = rng.choice(post.sizes["sample"], n_draws, replace=True)
a, b = (post[k].to_numpy()[idx] for k in ("a", "b"))
assert np.corrcoef(a, b)[0, 1] > 0.8
```
*Источник: `notes/2026_Orduz_bg-nbd-pymc.md`, ош. 1.*

**6. Диагностика MCMC читается из чисел, а не с графика.**
Не меньше двух цепочек (иначе `r_hat` не определён); burn-in задаётся параметром
`tune`, ручная индексация трейса запрещена; из `az.summary` берутся `r_hat` и
`ess_bulk`, а не только `mean`.
```python
s = az.summary(trace)
assert (s.r_hat < 1.01).all() and (s.ess_bulk > 400).all(), s.nsmallest(5, "ess_bulk")
```
*Источник: `notes/2026_Antonio_TDS-bg-nbd-series.md`, Part 3 ош. 3 (одна цепочка,
75% выборки выброшено, «no obvious sign of non-convergence» по блуждающим трейсам);
`notes/2026_Orduz_bg-nbd-pymc.md` — измерение того же на той же модели, ess 108.*

## 6. Тон текста

- Деловая проза. Без восклицательных знаков, без «впечатляющих результатов»,
  без обращений к читателю.
- Числа с единицами и периодом: не «выручка выросла», а «выручка когорты
  2011-Q3 за 6 месяцев: +18% к когорте 2011-Q2».
- Сравнительное утверждение состоит из четырёх элементов: метрика, окно,
  бейзлайн, доверительный интервал — и рядом стоит номер таблицы или графика.
  «Вероятностная модель точнее» без этих четырёх не имеет формы, в которой его
  можно вписать. Наречия «обычно», «как правило», «значительно» не заменяют
  ни один из элементов.
- Термины английские, проза русская. Второй язык README — по необходимости.
- Активный залог, первое лицо: «сравнил», «отверг», «выбрал».

## 7. Записи в журналах

`sync_check.py` считает журнал содержательным, если в секциях «Журнал решений»
или «Что не сработало» есть строка, начинающаяся с даты `ГГГГ-ММ-ДД` или с `- `.
Пиши записи так, иначе журнал не попадёт в напоминания о заливке.

```
2026-09-14 · взял Online Retail II · есть повторные покупки · Olist отверг: разреженность
- Gamma-Gamma не применил: корреляция frequency и monetary 0.31, допущение нарушено
```

## 8. Библиотека `ltv-clv-library/`

Отдельная от репозитория папка с теорией. Не публикуется: в ней чужие PDF
и сырые конспекты.

```
ltv-clv-library/
├── papers/     статьи и главы книг, как скачаны
├── notes/      конспекты: один файл на источник
└── drafts/     черновики собственных текстов и формул
```

**Именование статей:** `ГГГГ_Фамилия_короткое-название.pdf`
`1987_Schmittlein_pareto-nbd.pdf`, `2005_Fader_counting-your-customers.pdf`

**Конспект:** `notes/1987_Schmittlein_pareto-nbd.md`, тот же стем, что у PDF.
Минимум в конспекте — четыре строки:

```markdown
# <Источник>
**Допущения модели:** 
**Когда работает:** 
**Когда ломается:** 
**Что беру в кейс:** 
```

**Правило перехода библиотека → кейс.** Статья сама по себе в кейс не попадает.
Попадает решение: когда из конспекта следует выбор модели или параметра, это
пишется строкой в журнал `case_*.md` со ссылкой на файл конспекта. В README
кейса ссылка на источник даётся текстом (автор, год, название), а не путём к PDF.

**Как ссылаться в коде и текстах:** `from paths import LIBRARY` →
`LIBRARY / "notes" / "1987_Schmittlein_pareto-nbd.md"`.
